# Database Layer

The project supports **MySQL 8.0** and **PostgreSQL 16** from the same application SQL. Only the storage definitions live here; every query used by the API is in `server/src/queries/`.

## Layout

```text
database/
├── mysql/
│   ├── 01_schema.sql   # DDL: tables, keys, checks, indexes
│   └── 02_seed.sql     # demo accounts, lots, auctions, bids, settlements
└── postgres/
    ├── 01_schema.sql
    └── 02_seed.sql
```

Both folders are mounted at `/docker-entrypoint-initdb.d` by their Compose override (`docker/compose.mysql.yml`, `docker/compose.postgres.yml`). The official images execute the files in filename order **only when the data volume is empty**.

## Logical schema

```text
buyers ─┐                     ┌─ sellers
        ├── bids ── items ── auctions
        └── transactions ────┘
admins (back office, no domain relations)
```

| Table | Columns that matter | Rules |
|-------|--------------------|-------|
| `admins` | `id`, `username`, `password_hash` | Unique username |
| `buyers` | `id`, `username`, `password_hash`, `email`, `address`, `account_balance` | Unique username/email, balance ≥ 0 |
| `sellers` | same shape as buyers | Unique username/email, balance ≥ 0 |
| `items` | `id`, `seller_id`, `name`, `description`, `starting_price`, `category`, `image_url` | Seller FK, starting price ≥ 0 |
| `auctions` | `id`, `item_id`, `start_time`, `end_time`, `status`, `reserve_price` | One row per item, `end_time > start_time`, status ∈ scheduled/active/closed |
| `bids` | `id`, `item_id`, `bidder_id`, `amount`, `status` | Item/bidder FKs, amount > 0, status ∈ winning/outbid/won/lost |
| `transactions` | `id`, `item_id`, `buyer_id`, `seller_id`, `amount`, `status`, `payment_method` | One settlement per item, amount > 0, constrained status and method |

Primary keys are UUIDs generated by the API (`crypto.randomUUID()`). That keeps inserts identical on both engines and removes the `SELECT MAX(id) + 1` race the original project had.

`items` deliberately does **not** store a denormalized "last bid": the catalogue query derives `current_bid` and `bid_count` from `bids` with correlated subqueries, so there is one source of truth for bid state.

`auctions.status` is a cache. Reads derive the effective status from `start_time`/`end_time` with a portable SQL `CASE`, and a successful bid persists the transition inside its transaction. This keeps scheduled auctions correct without a background scheduler.

## Constraints and indexes

- Foreign keys are declared table-level and therefore enforced: MySQL/InnoDB and PostgreSQL both reject orphan rows.
- `CHECK` constraints validate prices, bid amounts, auction windows, and status vocabularies.
- Secondary indexes: `items(seller_id)`, `auctions(status, end_time)`, `bids(item_id, amount)`, `bids(bidder_id)`, `transactions(buyer_id)`, `transactions(seller_id)`.
- Money uses `DECIMAL(12,2)` on MySQL and `NUMERIC(12,2)` on PostgreSQL.

## Dialect differences

| Concern | MySQL 8.0 | PostgreSQL 16 |
|---------|-----------|---------------|
| Primary key type | `CHAR(36)` | `UUID` |
| Timestamps | `DATETIME` | `TIMESTAMPTZ` |
| "now" in seed | `UTC_TIMESTAMP()` | `NOW()` |
| Relative dates | `DATE_ADD(..., INTERVAL n DAY)` | `NOW() + INTERVAL 'n days'` |
| Table options | `ENGINE=InnoDB`, `utf8mb4` collation | none |
| Case folding | `--lower-case-table-names=1` in Compose | identifiers fold to lowercase |
| Named-parameter compiler output | `?` | `$1`, `$2`, ... |

Application queries avoid dialect-specific syntax: no `RETURNING`, no `ON CONFLICT`/`ON DUPLICATE KEY`, no `ILIKE`, no `NULLS LAST`, and no database-generated IDs. Row locking uses `SELECT ... FOR UPDATE`, which both engines support inside a transaction.

## The single query source

`server/src/queries/` exports SQL strings written with `:named` parameters. `server/src/db/compile.js` walks the string, skips quoted text, comments, and `::` casts, and emits placeholders for the active driver while building the positional values array. `server/src/db/index.js` exposes `query`, `many`, `one`, and `transaction` on top of that compiler.

Example:

```js
// server/src/queries/items.js
const baseSelect = `
  SELECT i.id, i.name, s.username AS seller_username, a.status AS auction_status
  FROM items i
  JOIN sellers s ON s.id = i.seller_id
  JOIN auctions a ON a.item_id = i.id
`;
```

The controller passes `{ id }` and never sees a driver API.

## Seed dataset

| Rows | Contents |
|------|----------|
| 1 admin | `admin` / `Admin123!` |
| 3 sellers | `seller1` … `seller3` / `Seller123!` |
| 4 buyers | `buyer1` … `buyer4` / `Buyer123!` |
| 6 items + auctions | three active, one scheduled, two closed |
| 5 bids | including an outbid pair and two winning/won rows |
| 2 transactions | settled sales for the closed lots |

Timestamps are relative to container start (`now ± n days`), so the demo stays meaningful after a reset. Passwords are bcrypt hashes; the plaintext values above are the documented demo credentials.

## Editing the schema

1. Change **both** `database/mysql/` and `database/postgres/` files.
2. Keep identifiers lowercase and unquoted so the shared queries and both engines agree.
3. Keep the seed consistent with the constraints (e.g. statuses inside the `CHECK` lists).
4. Run `make db-reset DB=mysql` and `make db-reset DB=postgres`, then `make test-all`.
5. If the change affects an API payload, update `server/src/queries/`, the controller, and the client together.

## Keeping the hosted demo populated

The scheduled workflow `.github/workflows/demo-topup.yml` only adds data. It counts active auctions and, when there are fewer than four, creates new lots as the seeded sellers with fresh timestamps and two bids each from the seeded buyers. Lot names, descriptions, categories, and prices are generated with Faker on every run, so there is no fixed catalogue to maintain. Existing accounts, lots, bids, and transactions are never deleted.

Run it manually against the hosted database with:

```bash
cd server
ALLOW_DEMO_TOPUP=true DEMO_DATABASE_URL="postgresql://..." DB_SSL=true pnpm db:demo-topup
```

Safety guards: `ALLOW_DEMO_TOPUP=true` must be set, `DEMO_DATABASE_URL` is required, and the script refuses localhost/private hosts so it cannot touch a development database.

## Inspecting data

```bash
make db-shell DB=mysql       # mysql -u auction_user -p auction_system
make db-shell DB=postgres    # psql -U auction_user -d auction_system
make adminer                 # http://localhost:8080
```

From the host: MySQL on `127.0.0.1:3306`, PostgreSQL on `127.0.0.1:5433` (configurable in `.env`).
